## What is already correct (verified, no change)
- **Email-gated order lookup holds.** `GET /api/orders/lookup?orderNumber=ORD-MKEUZVG5&email=surya@gmail.com` → **200**; same order with `email=attacker@evil.com` → **404**. Both `/api/orders/lookup` and `/api/orders/:orderNumber` return a reduced projection (order_number, status, items limited to product_name/quantity/width/height, subtotal/tax/shipping/total, shipping_address, tracking) — **no** manufacturer cost or margin. The BUG-F001 hardening is present and working.
- **No cross-customer IDOR in the account order list.** `GET /api/customer/orders` filters `db.orders` by the authenticated customer's own email (`server.js:17488`), not by a client-supplied id — a customer sees only their own orders.
- **Admin returns + warranty routes are auth-gated.** `GET /api/admin/returns` → **401** without a token, **200** with the admin token; same posture for `/api/admin/warranty-claims`. Consistent with the Stage-D RBAC fix.
- **Returns refund flow has integrity guards.** `POST /api/admin/returns/:id/refund` rejects a refund unless the return is `approved` (`server.js:14416`), blocks double-refund (`status === 'refunded'` → 400, `server.js:14411`), writes a `refund_paid` ledger entry, and updates the order to `refunded` with `refund_amount` (`server.js:14428-14457`).

## CONFIRMED defects

### BUG-H001 — Entire CRM/OMS/Finance router mounted PUBLICLY (no auth) — customer tracking routes plus invoice/PII/margin/P&L all reachable with no token  🔴
- **Route/code:** `app.use('/api/v1', crmRoutes)` (`server.js:463`) and `app.use('/api/public', crmRoutes)` (`server.js:469`) mount the **whole** `routes/crm-routes.js` router with no middleware. Only `/pricing/calculate` and `/track` were intended public (the `server.js:462` comment says "Public pricing endpoint (no auth)").
- **Severity:** **P1** · **Category:** Broken access control / mass IDOR + internal-financials & PII leak (OWASP A01; blueprint §15.1 "margin is internal … zero unauthorized cross-role access"). Same class as Stage-14 BUG-G001/G002.
- **Root cause:** mounting a router that contains admin-grade OMS/finance handlers at a public prefix exposes **every** route in it — including the Stage-15 tracking routes (`/track/:orderNumber`, `/orders/:id/status-history`) and, as collateral blast radius, the finance/invoice handlers. The parallel `authMiddleware`-gated mount at `/api/admin/crm` (`server.js:466`) is the *only* one that should exist for the non-public handlers. Stage-14 hardened the standalone `GET /api/invoices/:id/print` (BUG-G002) but this **separate** crm-router exposes an equivalent invoice read that was never gated.
- **Real-time example (reproduced, unauthenticated GET):**
  - `GET /api/v1/invoices` → **200**, returns all 10 invoices with customer PII and internal economics — response scan: **106** `manufacturerCost`, **12** `marginPercent`, **12** `marginAmount`, **10** `internalNotes` occurrences, plus `customer:{name,email:"Surya@gmail.com",phone:"8169449009",address:"205 Blue Jasmine Trl, Georgetown, TX 78628, US"}`.
  - `GET /api/public/invoices` → **200** (second public mount, identical leak).
  - `GET /api/v1/invoices/<id>` → **200** (single-invoice read).
  - `GET /api/v1/finance/summary` → **200** (P&L object), `GET /api/v1/finance/tax-report` → **200**, `GET /api/v1/finance/expenses` → **200**, `GET /api/v1/price-rules` → **200**, `GET /api/v1/manufacturer-prices` → **200** — all with no token.
  - Write handlers in the same router (`PUT /orders/:id/status` `crm-routes.js:528`, `POST /invoices` `:772`, `POST /orders/:orderId/shipments` `:615`, `PUT /shipments/:id` `:666`) are mounted at the same public prefixes. A no-auth caller could transition order status or mint invoices. **[NEEDS-WRITE-TEST]** — not exercised (read-only pass), but the mount + handler code confirm the exposure.
- **Proposed fix (native-first, needs approval):** stop mounting the full CRM router publicly. Keep only the genuinely public handlers under a public prefix (a thin router with `/pricing/calculate` and a re-scoped `/track`); leave the rest exclusively under `app.use('/api/admin/crm', authMiddleware, crmRoutes)`. Concretely: delete the `app.use('/api/public', crmRoutes)` line and narrow `app.use('/api/v1', ...)` to a whitelist router, so invoices/finance/price-rules/manufacturer-prices/order-status-write are unreachable without an admin token. Cross-ref Stage-14 BUG-G002 (same margin/PII class, different route).

### BUG-H002 — Public order-tracking endpoint has no token verification (designed IDOR) and is silently dead due to an `orderNumber` vs `order_number` field mismatch  🟠
- **Route:** `GET /track/:orderNumber` (`routes/crm-routes.js:1260`), reachable at `/api/v1/track/:orderNumber` and `/api/public/track/:orderNumber` (both public per BUG-H001).
- **Severity:** **P2** (P3 broken-feature today + latent P1 IDOR) · **Category:** Broken access control (latent) + dead customer-facing tracking (Stage 15.3 / 12.3).
- **Root cause:** two defects in one handler. (1) The handler reads the `token` query param but never checks it — the code comment states *"In production, verify token matches order. For now, allow access with any token or email verification"* (`crm-routes.js:1273-1274`). There is no email or token match, so once functional it returns any order's status history + shipment tracking to any caller = IDOR. (2) It matches `o.orderNumber === req.params.orderNumber`, but orders on disk store the field as **`order_number`** (snake_case; `orderNumber` is `undefined` on every order). The match therefore never succeeds → the route is dead. It also reads `db.orderStatusHistory` (the crm-router's separate 6-row store, snake-free schema `fromStatus/toStatus/changedBy`) rather than the order's own inline `status_history`, so even its data source is disconnected from the live order records.
- **Real-time example (reproduced):** `GET /api/public/track/ORD-MKEUZVG5` → **404** `{"success":false,"error":"Order not found"}`; `GET /api/v1/track/ORD-MKEUZVG5` → **404**. The order exists (`/api/orders/lookup` returns it 200), so the 404 is purely the field mismatch. Customer-facing tracking via this route is non-functional today; the moment the field name is corrected it leaks tracking/status data with no auth.
- **Proposed fix (native-first, needs approval):** if this route is retained, (a) match on `o.order_number || o.id`, (b) require the same credential pair as `/api/orders/lookup` (order number + matching `email`, or a signed per-order token) before returning anything, and (c) read the order's inline `status_history`. If the working customer path is already `/api/orders/lookup` (it is — `order-lookup.html` uses it), the simpler fix is to remove `/track` from the public surface entirely under BUG-H001.

### BUG-H003 — `/api/customer/orders` returns the raw order to the customer, leaking internal manufacturer cost + margin (Stage 15.3)  🟠
- **Route:** `GET /api/customer/orders` (`server.js:17477`, `customerAuthMiddleware`).
- **Severity:** **P2** · **Category:** Internal-financials leak into a customer-facing surface (blueprint §15.1 "margin is internal … customers never see it"). Same margin-leak class as Stage-14 BUG-G002, here on the account/order-history endpoint.
- **Root cause:** the handler returns the **unprojected** order object (`res.json({ orders })`, `server.js:17491`). Live orders carry internal economics: `order.pricing.manufacturer_cost_total`, `order.pricing.margin_total`, `order.pricing.margin_percent`, and per-item `items[].price_snapshot.manufacturerCost`. Unlike the public lookup routes (which strip to a customer-safe projection), the account order list forwards everything, so a logged-in customer viewing "My Orders" receives the store's manufacturer cost and margin.
- **Real-time example:** on-disk order `ORD-MKEUZVG5` (returned verbatim by this route) contains `order.pricing` keys `subtotal, tax, shipping, total, manufacturer_cost_total, margin_total, margin_percent` and **7** `manufacturerCost` / **4** `margin` occurrences inside `items[].price_snapshot`. Code path confirms no projection is applied before send. (Live fetch requires a customer JWT; the sample customers use bcrypt passwords not available to this read-only pass, so the leak is confirmed at the code + data layer, with the client `account.html` rendering only a subset — the raw payload still ships over the wire.)
- **Proposed fix (native-first, needs approval):** apply a customer-safe projection in `/api/customer/orders` (mirror the `/api/orders/lookup` shape) that strips `pricing.manufacturer_cost_total`, `pricing.margin_total`, `pricing.margin_percent`, and every `price_snapshot.manufacturerCost`/`margin*` before responding.

### BUG-H004 — Reorder is non-functional: it writes a legacy `localStorage` cart that the cart page ignores (Stage 15.5)  🟡
- **Route/code:** `account.html` `reorderItems()` (`frontend/public/account.html:1811`) and `cart.html` `loadCart()` (`frontend/public/cart.html:482`).
- **Severity:** **P3** · **Category:** Broken repeat-purchase workflow / two competing cart systems.
- **Root cause:** `reorderItems()` pushes the order's items into `localStorage.setItem('cart', ...)` and redirects to `/cart.html`. But `cart.html`'s `loadCart()` reads **only** the server session cart (`GET /api/cart/${sessionId}` → `cartItems = result.data`, `cart.html:486-490`) and never reads `localStorage.cart`. The reordered items are written to a store the cart page does not consume, so they silently vanish — clicking "Reorder" lands the customer on `/cart.html` showing the unchanged server cart. (The legacy `localStorage.cart` is still written by `cart.html`'s own updateQuantity/removeItem as migration residue, which is why it looks live but isn't the source of truth.) Stage 15.5 repeat-purchase produces no observable effect.
- **Real-time example (reproduced by code inspection):** `reorderItems()` → `localStorage.cart = [...items]` then `location.href='/cart.html'`; `loadCart()` → fetches `/api/cart/:sessionId`, ignores `localStorage.cart`. Net: items added by reorder never appear.
- **Proposed fix (native-first, needs approval):** route reorder through the server cart — for each item POST to `/api/cart` with `{configuration, width, height, quantity, extendedWarranty}` so the server re-prices against the **current** catalog (the cart engine already recalculates server-side and ignores client price, per Pass-4). This also fixes a latent staleness risk: reorder currently copies the historical `unit_price`/`price_snapshot`, so a fabric price change or a discontinued fabric would carry a stale/invalid price if the localStorage path ever worked. Re-pricing + fabric-availability check on reorder is the correct native behavior.

### BUG-H005 — Customer "View/Print Invoice" links to an admin-only page (Stage 15.3)  🟡
- **Code:** `account.html` `viewInvoice()` (`frontend/public/account.html:1806`) opens `/admin/invoices.html?view=${orderId}&print=true`.
- **Severity:** **P3** · **Category:** Broken customer-facing flow + information-architecture/security smell.
- **Root cause:** the customer account page sends customers to an **admin** URL. `/admin/invoices.html` is an admin surface whose data loads require an admin JWT (which a customer never has), so the customer cannot view/print their own invoice from their account. A hardened customer-facing invoice endpoint already exists — `GET /api/invoices/:id/print` (customer-safe projection, Stage-14 BUG-G002 fix) — and should back this button instead. Routing customers into `/admin/*` is also an IA/security smell.
- **Real-time example:** `GET /admin/invoices.html` serves the static admin page (200), but its invoice data fetch is admin-gated; a customer clicking "View/Print Invoice" reaches an admin screen that cannot render their invoice.
- **Proposed fix (native-first, needs approval):** point `viewInvoice()` at the customer print surface (the print-invoice page backed by `GET /api/invoices/:id/print`), keyed by the customer's own invoice id, instead of `/admin/invoices.html`.

### BUG-H006 — Public warranty-claim status uses enumerable timestamp IDs and returns free-text resolution; claim submission has no order-ownership check  🟡
- **Routes:** `GET /api/warranty-claims/:id/status` (`server.js:14582`, no auth) and `POST /api/warranty-claims` (`server.js:14505`, no auth).
- **Severity:** **P4** · **Category:** Weak-identifier IDOR surface + missing ownership validation (abuse vector). No live data leak today (0 warranty claims seeded).
- **Root cause:** (1) claim IDs are `WC-${Date.now()}` (`server.js:14526`) — a 13-digit millisecond timestamp, trivially enumerable — and the public status route returns `status` plus a free-text `resolution` field with no auth, so any guessed id discloses claim state and whatever internal text staff put in `resolution`. (2) `POST /api/warranty-claims` looks up the order optionally (`order?.id || null`, `server.js:14528`) and never verifies the submitter owns it — any email + any order number files a claim; when `customerName` is omitted it back-fills the real `order.customer_name` into the claim record. No customer PII is *returned* to the submitter (the confirmation email goes to the submitter-supplied address), so impact is spam/abuse and weak-id enumeration rather than a read leak.
- **Real-time example (reproduced read-only):** the status route is reachable with no auth (returns 404 for a non-existent id since the store is empty); the ID scheme is confirmed in code as `WC-<Date.now()>`. Submission ownership gap confirmed by code (no email/token match against the resolved order).
- **Proposed fix (native-first, needs approval):** issue opaque claim IDs (uuid) instead of `Date.now()`; require order-number + matching email on both submission and status lookup (reuse the `/api/orders/lookup` credential check) so a claim can only be filed/queried by the order owner; and ensure the public status projection excludes any internal `resolution` notes (return a coarse status enum only).
