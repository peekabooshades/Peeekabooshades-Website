# Stage 10 — Order Created & Internal Project Record (Order Agent) — Audit

> Section **J** of the recursive audit loop. Scope: customer-journey **Stage 10** — 10.1 create order + capture all config, 10.2 `orders/create` → internal project record, 10.3 normalized order state machine. Focus is order **creation** + the internal-project mirror + the **state machine itself**. Stages 11 (manufacturing), 12 (fulfillment/F), 13 (installation), 14 (invoicing/G) are audited elsewhere and are **not** re-litigated here except where a Stage-10 defect leaks into them. **Read-only.** Reproduced against the running app on `http://localhost:3001` (admin token) with sample data in `backend/database.json` (12 real orders, 10 customer invoices). Only GETs + the read-only pricing POST were issued; `database.json` was not modified (byte size 1,330,598 unchanged across the run). Native-first, recommendation-only — no fixes applied, no writes.

## Severity key
P0 security/data-loss · P1 checkout/pricing/order failure · P2 major workflow failure · P3 partial feature / usability · P4 cosmetic.

## Surface audited
- **Two divergent order-creation paths funnel into `db.orders`:**
  - **LIVE / storefront:** `POST /api/orders` (`server.js:953`), called by `frontend/public/cart.html:1204`. Status `pending`, **flat** schema (`customer_name`/`customer_email`), **client-supplied** subtotal/tax/shipping, uses server.js's **own** DB cache.
  - **Unused-by-storefront:** `POST /api/checkout` (`server.js:1189`) → `order-service.createOrderFromCart` (`order-service.js:78`). Status `order_placed`→`order_received`, **nested** `customer{}` schema, **server-recomputed + rounded** totals, `db-loader` cache, ledger entries, analytics, creation history.
  - Additional paths: `POST /api/dealer/orders` (`server.js:9777`, `dealerService.createDealerOrder`), `POST /api/v1/orders` (`server.js:14001`, API-key, fires `triggerWebhook('order.created')`).
- **State machine:** `ORDER_STATES` + `VALID_TRANSITIONS` (`order-service.js:12-41`), guard `canTransition` (`:70`), guarded endpoint `POST /api/orders/:orderId/transition` (`server.js:1299`, authed) → `transitionOrderStatus` (`order-service.js:370`). Manufacturer subset `MFR_VALID_TRANSITIONS` (`manufacturer-service.js:21`), `updateOrderStatus` (`:253`), `addTrackingInfo` (`:323`). Admin `PUT /api/admin/orders/:id/status` (`server.js:2251`) with its own flat `validStatuses` list (`:2263-2282`) and `validateOrderReceivedTransition` (`:2176`).
- **Persistence:** three writers to one JSON file — server.js inline cache (`server.js:270-294`), `services/db-loader` cache (`db-loader.js:20-43`), and **direct** `fs.writeFileSync` in `routes/payment-routes.js` (`:592/611/631`), `routes/crm-routes.js:45`, `services/content-manager.js:34`.
- **Sample-data facts:** 12 orders; status distribution `{order_received:1, order_placed:1, shipped:5, manufacturing:1, pending:4}`. **All 12 are flat-schema** (0 nested) — i.e. every real order came through the LIVE `/api/orders` path. Order totals are stored **unrounded** (e.g. `159.14915000000002`, `91.44812499999999`). 2 orders have **no invoice**. `/api/order-statuses` config vocabulary omits `pending` (and `ready_to_ship`), yet 4 orders are `pending`.

## What is already correct (verified, no change)
- **The state machine is sound *where it is actually invoked*.** `transitionOrderStatus`/`canTransition` correctly reject illegal transitions, append to `db.orderStatusHistory`, and write an audit-log entry (`order-service.js:382,404-430`). The `POST /api/orders/:orderId/transition` endpoint is admin-authed (`server.js:1299`).
- **`createOrderFromCart` (the `/api/checkout` path) is the correct implementation:** recomputes subtotal/tax/total server-side **with rounding** (`order-service.js:146-151`), validates frozen price snapshots + 24h staleness + cart/snapshot parity and blocks checkout on mismatch (Ticket 010, `:87-138`), records a creation-time status-history row (`:317`), and creates ledger entries + analytics at the endpoint (`server.js:1213-1216`). It is simply **not the path the storefront uses**.
- **Order↔invoice totals are consistent by inheritance** — the auto-invoice copies the order total verbatim; live check found **0** order/customer-invoice total mismatches (>0.01). (Both are equally *unrounded* — the rounding defect itself is Stage-14 BUG-G003, not re-litigated.)
- **`validateOrderReceivedTransition`** provides invoice-exists / invoice-total-parity / manufacturer-cost-present reconciliation checks at the `order_received` milestone (`server.js:2176-2248`).
- **Customer dedup on creation** by email then normalized phone (`server.js:971-1008`) — avoids duplicate customer rows per order.
- **Manufacturer transitions are guarded within their subset** via `MFR_VALID_TRANSITIONS` (`manufacturer-service.js:265-268`) — except `addTrackingInfo` (see BUG-J004).

## Internal project-record mirror — documented gap (recommendation-only)
Stage 10.2 and blueprint §11.6 mandate an **internal project record created via a verified, idempotent `orders/create` webhook** that mirrors the order for operational milestones. **No such record or consumer exists** — there is no `db.projects`, no `createProject`, and no `orders/create` webhook handler; operational data (manufacturer assignment, status timestamps) is written **onto the order object itself**. There is also **no idempotency key** on any creation path. Per the no-own-assumptions rule this is reported as a gap, not invented. See **BUG-J007**.

## CONFIRMED defects

### BUG-J001 — Live checkout trusts client-supplied subtotal/tax/total; server never recalculates (price/financial tampering)  🔴
- **Route/code:** `POST /api/orders` (`server.js:953-1082`); storefront payload `frontend/public/cart.html:1184-1198`.
- **Severity:** **P1** · **Category:** Pricing/financial integrity (blueprint §4 "server-authoritative price"; §15 pricing is server-side).
- **Root cause:** `cart.html` computes `subtotal`, `tax = subtotal * taxRate`, `shipping` **client-side** and POSTs them. The server uses them verbatim: `total = subtotal + (tax||0) + (shipping||0)` (`server.js:964`) and `marginTotal = subtotal - totalMfrCost` (`:1043`). The handler *has* the cart items in hand (`db.cart.filter`, `:1013`) but **never** recomputes or cross-checks the client subtotal against the sum of line totals. Order, the auto-generated customer invoice (`:1103`), and the margin/ledger economics all inherit attacker-controllable numbers. The correct path (`createOrderFromCart`) recomputes server-side — but the storefront does not call it.
- **Real example (reproduced, read):** live order `ORD-MKJ4TFA8` stored `subtotal 175.5, tax 14.478750000000002, total 189.97875` exactly as the client sent them. A crafted `POST /api/orders {subtotal:1,tax:0,shipping:0,...}` would create a **$1** order + $1 invoice for the same cart. **[NEEDS-WRITE-TEST]** to submit a tampered payload (POST is out of read-only scope).
- **Proposed fix (native-first, recommendation-only):** point the storefront at `POST /api/checkout` (which already recomputes + rounds server-side), or make `/api/orders` ignore client subtotal/tax and recompute from `db.cart` line totals using the same `extendedPricingEngine` + `Math.round(...*100)/100` the checkout path uses. Then delete the client-trusted branch.

### BUG-J002 — Live checkout writes orders into `pending`, a state absent from the state machine → cannot advance via the transition engine, and no creation audit row  🔴
- **Route/code:** `POST /api/orders` sets `status:'pending'` (`server.js:1059`); `ORDER_STATES`/`VALID_TRANSITIONS` (`order-service.js:12-41`).
- **Severity:** **P2** · **Category:** State-machine integrity / audit gap (Stage 10.3).
- **Root cause:** `'pending'` is not a key in `VALID_TRANSITIONS`, not in `ORDER_STATES`, and not in the `/api/order-statuses` config. `transitionOrderStatus` → `canTransition('pending', X)` → `VALID_TRANSITIONS['pending'] || []` → `[]` → **throws `Invalid transition from pending to X`**. So an order created by the live storefront **can never be moved by the guarded transition endpoint**. Separately, `/api/orders` pushes **no** `db.orderStatusHistory` row on creation (confirmed absent in `server.js:1084-1121`) — unlike `createOrderFromCart` (`order-service.js:317`) — so live orders have **zero** creation audit trail.
- **Real example (reproduced):** 4 of 12 orders are `pending`; `GET /api/admin/orders/ORD-MKJ4TFA8` → `status:'pending'`, `status_history:false` (length 0), no `orderStatusHistory` entry. The `/api/order-statuses` vocabulary does not even list `pending`.
- **Proposed fix:** create live orders in the canonical initial state (`order_placed`) and record a `fromStatus:null → order_placed` history row + audit entry at creation (mirror `order-service.js:317`).

### BUG-J003 — Admin status endpoint bypasses the state machine entirely (any transition accepted) and uses a divergent 18-value vocabulary  🔴
- **Route/code:** `PUT /api/admin/orders/:id/status` (`server.js:2251-2356`), `validStatuses` (`:2263-2282`). This is the endpoint the admin UI (`admin/orders.html`) actually calls; the guarded `/api/orders/:orderId/transition` is effectively unused by the UI.
- **Severity:** **P2** · **Category:** State-machine integrity — "portals cannot force invalid states" (blueprint §11.6) is violated.
- **Root cause:** the handler validates only that `status ∈ validStatuses` (a flat 18-entry list including `pending`, `payment_received`, `sent_to_manufacturer`, `in_manufacturing`, `in_testing`, `in_shipping`, `closed`, `disputed` — **none of which are in `ORDER_STATES`**) and then assigns `order.status = status` (`:2307`) with **no `canTransition()` check**. Any jump is accepted — e.g. `delivered → manufacturing`, `refunded → shipped`, `cancelled → qa`. Three disjoint status vocabularies now coexist: order-service (12 states, guarded), admin PUT (18, unguarded), `/api/order-statuses` config (~10). `validateOrderReceivedTransition` is applied only for `order_received` and is **soft (warnings only, admin proceeds)** (`:2296`).
- **Real example (reproduced):** `/api/order-statuses` returns `order_placed, order_received, manufacturing, qa, shipped, delivered, issue_reported, refund_requested, ...` — it **omits** `pending`, `payment_received`, `ready_to_ship`, yet `pending` orders exist and the admin PUT accepts all 18 of its own list. No transition guard runs on the admin path at all.
- **Proposed fix:** route admin status changes through `transitionOrderStatus` (or add `canTransition` enforcement + a single shared status enum) so the admin portal is bound by the same state machine; keep the extra aliases only as display labels mapped to canonical states.

### BUG-J004 — Manufacturer `ready_to_ship` is an orphan state admin/state-machine cannot move (cross-agent dead-end); `addTrackingInfo` skips transition validation; doc drift  🟠
- **Route/code:** `MFR_VALID_TRANSITIONS` (`manufacturer-service.js:21-27`), `addTrackingInfo` (`:340-363`); admin `validStatuses` (`server.js:2263-2282`); `docs/ORDER_LIFECYCLE.md:87-92`.
- **Severity:** **P2** · **Category:** Cross-agent handoff / state-machine integrity.
- **Root cause (three parts):** (1) The manufacturer machine adds `ready_to_ship` (`qa → ready_to_ship → shipped`), a state that exists in **no** other machine — not `ORDER_STATES`, not admin `validStatuses` (0 occurrences), not `VALID_TRANSITIONS`. Once a manufacturer sets `ready_to_ship`, admin PUT rejects any change (`Invalid status`) and `/transition` can't move it (`VALID_TRANSITIONS['ready_to_ship']` undefined → `[]`); **only the manufacturer portal** can advance it. If the manufacturer stops, the order is stuck with no admin recourse (can't even cancel). (2) `addTrackingInfo` sets `order.status = 'shipped'` **directly** (`:355`) with no `MFR_VALID_TRANSITIONS` check — so from *any* non-terminal state (incl. `order_received`, before manufacturing/QA) adding tracking jumps straight to `shipped`, skipping production/QA. (3) `docs/ORDER_LIFECYCLE.md:87-92` documents manufacturer `qa → [shipped, manufacturing]`; the **code** says `qa → [ready_to_ship, manufacturing]` — the doc's authoritative matrix is wrong.
- **Real example:** code inspection — `MFR_VALID_TRANSITIONS['ready_to_ship'] = ['shipped','qa']` (`manufacturer-service.js:25`) vs admin `validStatuses` (no `ready_to_ship`, `server.js:2263-2282`) vs `VALID_TRANSITIONS` (no `ready_to_ship` key, `order-service.js:28-41`). `addTrackingInfo` bypass at `manufacturer-service.js:352-355`.
- **Proposed fix:** add `ready_to_ship` to the canonical `ORDER_STATES` + `VALID_TRANSITIONS` (with `ready_to_ship → shipped/qa` and an admin path in/out) so all three machines agree; make `addTrackingInfo` call the validated transition instead of assigning status directly; correct `docs/ORDER_LIFECYCLE.md`.

### BUG-J005 — Three incoherent caches over one `database.json`; direct-write payment webhook is silently overwritten (lost update / data-loss)  🔴
- **Route/code:** server.js inline cache (`server.js:270-294`, 30s TTL), `db-loader` cache (`db-loader.js:20-43`, 30s TTL, returns a **shared object reference**), direct `fs.writeFileSync` in `routes/payment-routes.js:592/611/631`, `routes/crm-routes.js:45`, `services/content-manager.js:34`.
- **Severity:** **P1** · **Category:** Data integrity / lost update (blueprint §15 "reconciliation"; §APIs "idempotent, dead-letter on failure").
- **Root cause:** three writers with independent, non-invalidated caches all overwrite the whole 1.3MB file via non-atomic `writeFileSync`. The Stripe webhook (`payment_intent.succeeded`) reads the file directly, sets `order.paymentStatus='paid' / stripePaymentIntentId / paidAt`, and writes it back (`payment-routes.js:585-592`). Meanwhile server.js and db-loader may hold a **pre-payment** copy for up to 30s; the next `saveDatabase(db)` from either cache rewrites the entire file, **erasing the paid flag**. The code already acknowledges the dual-cache hazard (BUG-F005 comment, `server.js:296-304`; targeted `invalidateCache()` at `:2368`) but only patches the *shipped-profit* path — the payment-webhook writer and CRM writer are **not** covered. Non-atomic writes also risk truncating/corrupting `database.json` on a crash mid-write.
- **Real example:** `payment-routes.js:588-592` writes `db.orders[i].paymentStatus='paid'` directly to disk; any concurrent order/status write from the cached path (`saveDatabase`, `server.js:291`, or `saveDB`, `db-loader.js:40`) will clobber it because neither cache was invalidated by the direct write. **[NEEDS-WRITE-TEST]** to race two writers and observe the lost `paid` flag.
- **Proposed fix:** funnel **all** DB writes through a single module (db-loader) with a write lock (or atomic temp-file + `rename`), and have direct writers invalidate/participate in that cache; longer-term, this is the native argument for moving transactional order/payment state to Shopify + a real datastore rather than a shared JSON file.

### BUG-J006 — Payment state fragmented across `order.payment.status`, `order.paymentStatus`, and flat webhook fields; order status desynced from payment (no single `financial_status`)  🟠
- **Route/code:** `order-service.js:261-266,393-395`; `server.js:1061-1066`; `payment-routes.js:588-591`.
- **Severity:** **P2** · **Category:** Reconciliation (Stage 10.3 / 14.3).
- **Root cause:** there is no canonical `financial_status`. The checkout/order paths store `order.payment.status`; the Stripe webhook writes a **different** flat field `order.paymentStatus` (+`paidAt`,`stripePaymentIntentId`) that admin/order views don't read. `order_received` (state-machine meaning: "payment confirmed") only sets `payment.status='completed'` when reached via `transitionOrderStatus` (`order-service.js:393`) — which is unreachable for `pending`/admin-PUT orders (BUG-J002/J003) — so payment never reconciles with order progression.
- **Real example (reproduced):** `ORD-TEST-1768836005920` is `status:order_received` ("payment confirmed") yet `payment.status:'pending'`; `ORD-MKJ50MDQ` is `status:manufacturing` with `payment:undefined` (no payment object at all); `ORD-MKJ4TFA8` (`pending`) has `payment:undefined`. Order progression and payment state are independently mutable and diverge.
- **Proposed fix:** define one `order.financial_status` (`pending|paid|partially_refunded|refunded|failed`) written by every payment writer (webhook included), and make `order_received` conditional on it; deprecate the flat `paymentStatus` field.

### BUG-J007 — No internal project/CRM mirror record and no idempotency on order creation (Stage 10.2 unimplemented)  🟠
- **Route/code:** all creation paths (`server.js:953`, `:1189`, `:9777`, `:14001`); `order-service.js:335` (auto-assign).
- **Severity:** **P2** · **Category:** Missing workflow / architecture (Stage 10.2; blueprint §11.6). Recommendation-only, owner-gated.
- **Root cause:** Stage 10.2/§11.6 specify an internal project record created via a **verified, idempotent `orders/create` webhook** that mirrors the order. No project record, no webhook consumer, and no idempotency key exist; operational data is written onto the order itself and the only creation hook is `manufacturerAssignment.autoAssignManufacturer`, whose failures are silently swallowed (`order-service.js:349-352`). With no idempotency key, a double-submitted checkout creates two orders. Because there is **no mirror**, the stage's "do order and project stay consistent" question is moot — there is nothing to keep consistent.
- **Real example:** grep of `server.js` + `services/*.js` finds no `db.projects`/`createProject`/`orders/create` consumer; the demo `triggerWebhook('order.created')` (`server.js:14038`) fires only from the API-key `/api/v1/orders` path and posts to an external URL — it does not build an internal project record.
- **Proposed fix:** native-first, treat the Shopify order as SoT and add a thin idempotent backend project record keyed by Shopify order id (dedupe on webhook event id per the `order-status-sync` skill contract); until Shopify is wired, at minimum add an idempotency key to the creation endpoints.

### BUG-J008 — Order number `ORD-`+`Date.now().toString(36)` is collision-prone, unchecked for uniqueness, and format-inconsistent  🟡
- **Route/code:** `server.js:963` and `order-service.js:141` (identical formula); lookups `server.js:1142`, `order-service.js:447`, `manufacturer-service.js:171`.
- **Severity:** **P3** · **Category:** Data integrity / robustness.
- **Root cause:** `'ORD-' + Date.now().toString(36).toUpperCase()` has millisecond resolution and **no uniqueness check**. Two orders created in the same millisecond receive identical `order_number`. Every lookup uses `db.orders.find(o => o.order_number === x)` → returns the **first** match, making the second order reachable only by UUID (invisible to customer lookup, manufacturer view, transition-by-number).
- **Real example (reproduced):** live `order_number` values show inconsistent coexisting formats — `ORD-TEST-1768836005920`, `ORD-TEST-MB9S71`, `ORD-MKJ61VI2`, `ORD-MKJ5EGG2`. Same-ms collision is demonstrable in code; **[NEEDS-WRITE-TEST]** to force two creations within one millisecond and observe the duplicate.
- **Proposed fix:** add a monotonic per-day counter or random suffix and a post-generation uniqueness check against `db.orders`; standardize one format.

### BUG-J009 — Auto-invoice failure is swallowed → orphaned orders with no invoice; the live path creates no creation-time ledger  🟡
- **Route/code:** `server.js:1107-1109` and `:1225-1228` ("non-fatal" catch); ledger only on `/api/checkout` (`server.js:1213`).
- **Severity:** **P3** · **Category:** Orphaned records / financial completeness.
- **Root cause:** invoice creation is wrapped in a try/catch that logs and continues, so a failure leaves an order with **no invoice**, silently. Additionally, the LIVE `/api/orders` path creates **no** ledger entries at all (unlike `/api/checkout`'s `createOrderLedgerEntries`), so live orders have no financial ledger at creation. `validateOrderReceivedTransition` would flag `INVOICE_MISSING` but it is soft (warnings only — admin proceeds, `server.js:2296`).
- **Real example (reproduced):** 2 of 12 orders have no linked invoice — `ORD-TEST-1768836005920` (`order_received`) and `ORD-TEST-MB9S71` (`order_placed`) — i.e. orders sitting in payment-confirmed / placed states with no invoice mirror.
- **Proposed fix:** make invoice+ledger creation part of the same transaction as order creation (fail the order or queue a retry/dead-letter on invoice failure), and unify creation so both storefront and checkout paths produce invoice + ledger.

### BUG-J010 — Line-item snapshot field-name drift (`price_snapshot` vs `price_snapshots`) across creation paths  🟡
- **Route/code:** `/api/orders` preserves cart's `price_snapshot` (singular) verbatim (`server.js:1067-1070`); `createOrderFromCart` writes `price_snapshots` (plural, restructured) (`order-service.js:206`).
- **Severity:** **P3** · **Category:** Data-model consistency / snapshot integrity.
- **Root cause:** the two paths persist the immutable price snapshot under **different field names and shapes**. Consumers must defensively check both (`validateOrderReceivedTransition` `server.js:2210`; `manufacturer-service.js:238-239`); any consumer checking only one name silently sees no snapshot → false `MANUFACTURER_COST_MISSING` or lost margin data.
- **Real example (reproduced):** `ORD-MKJ4TFA8` items carry `price_snapshot` present / `price_snapshots` absent (keys `captured_at, manufacturer_price, margin, customer_price`).
- **Proposed fix:** normalize to one canonical field (`price_snapshots`) at creation in both paths; add a one-time migration alias for existing rows.

## Summary
Stage 10 is the weakest audited stage: the live storefront checkout (`POST /api/orders`) trusts client-supplied money, writes orders into a `pending` state the state machine cannot advance, records no creation audit/ledger, and the admin status endpoint bypasses the state machine entirely — while three incoherent caches over a single `database.json` (plus a direct-write payment webhook) create a real lost-update/data-loss path; the mandated idempotent order→project mirror does not exist.

**Confirmed defects: 10 — P1: 2 (J001, J005) · P2: 5 (J002, J003, J004, J006, J007) · P3: 3 (J008, J009, J010) · P4: 0.**
