# Stage 09 — Checkout & Payment (DEEP) — Audit (Checkout & Payment Agent)

> Section **G** of the recursive audit loop, **Stage 9** (the checkout + payment *act* itself — distinct from Stage 14 balance/invoicing, already covered in `stage-14-invoicing.md`). Scope: 9.1 line-item preservation, 9.2 shipping/tax, 9.3 full/deposit/terms, 9.4 coupons, plus checkout input validation, server re-pricing vs client-trust (price tampering), payment idempotency/double-charge, order-on-success vs order-on-failure, guest vs account, inventory/availability, and user-facing failure states. Reproduced read-only against the running app on `http://localhost:3001`. **READ-ONLY audit — no order placed, no payment run, no DB write.** DB `backend/database.json` md5 `806f71056b2e24945c90bd3de893083d` unchanged across the run (only `GET`s + the sanctioned read-only `POST /api/calculate-order-total`, which does not persist).

## Severity key
P0 security/payment/data-loss · P1 checkout/pricing/order failure · P2 major workflow failure · P3 partial feature / usability · P4 cosmetic.

## Surface audited
- **Live order-creation path (what the storefront actually calls):** `POST /api/orders` (`server.js:953`) — **no auth**; frontend `frontend/public/cart.html` → `createOrder()` (`cart.html:1180-1208`).
- **Orphaned "safe" path (defined but wired to nothing):** `POST /api/checkout` (`server.js:1189`) → `createOrderFromCart` (`services/order-service.js:78-365`).
- **Pricing/totals for checkout:** `POST /api/calculate-order-total` (`server.js:1558`, public) using `extendedPricingEngine`; `cart.html:523` consumes it for display.
- **Payment processors:** `routes/payment-routes.js` — Stripe intent (`:140`), Stripe confirm (`:211`), demo card (`:495`), PayPal (`:281/:326`), webhooks (`:549` Stripe, `:671` PayPal), refunds (`:745/:820`).
- **Coupon/discount:** `promoCode` accepted at `server.js:1560`; only real promo logic is `POST /api/v1/promo/validate` (`server.js:14078`, `apiKeyAuth`).
- **Auto-invoice at checkout:** `invoiceService.createInvoiceFromOrder(order.id,'customer')` fired from both `server.js:1103` (`/api/orders`) and `server.js:1221` (`/api/checkout`) — cross-ref **G003/G004** (stage-14).
- **Sample-data facts:** products carry `stock_status` (`in_stock`) and `is_active`; neither checkout path reads them. Demo payment methods report `configured:true` even with no real processor keys.

## What is already correct (verified, no change)
- **Processor-level idempotency exists** on the Stripe path: `create-intent` honors an idempotency key (`payment-routes.js:150-194`) and passes Stripe's own `idempotencyKey`. Prevents duplicate *charges* at the processor (does **not** prevent duplicate *orders* — see H006).
- **Stripe webhook signature** is verified when `STRIPE_WEBHOOK_SECRET` is set (`payment-routes.js:561`); demo decline card `4000000000000002` is simulated (`payment-routes.js:518`).
- **Server-side tax + shipping in `calculate-order-total`:** tax `subtotal*0.0725`, free shipping ≥ $99 (`server.js:1604-1612`), rounded to cents. (The *display/estimate* path is correct; the flaw is that the live **order** path does not use it — see H001.)
- **The orphaned `/api/checkout` path is actually the correct design:** `createOrderFromCart` re-prices from server-side cart snapshots, validates price freshness/parity (`PRICE_VALIDATION_FAILED`, `order-service.js:87-138`), guards empty cart (`:83`), and validates customer name+email (`server.js:1197`). It is simply **not wired to the storefront** (H005).
- **Line-item preservation (9.1):** cart items are copied into the order verbatim (`server.js:1067`, `order-service.js:154`) — configuration/fabric/dimensions survive into the order (consistent with Pass-4 "no data loss into cart/order").
- **Order-number/IDOR on lookup** already hardened (BUG-F001): `GET /api/orders/:orderNumber` now requires matching email (`server.js:1132-1145`).

## Deposit / payment-terms (9.3) — documented gap (NOT a new defect; cross-ref stage-14)
Journey **9.3** and the Checkout & Payment Agent doc both advertise "**full / deposit / payment terms**," and `GET /api/payments/methods` returns a "Pay by Invoice" option — but there is **no customer deposit-split, balance-due, or net-terms model** anywhere in checkout or the order/invoice schema. The only `paymentTerms` field in the code is on **manufacturers** (`server.js:3080`, `net30` for manufacturer POs), unrelated to customer checkout. Consistent with stage-14's finding (blueprint §12.5 marks deposit % as `[CONFIRM]`). Per the no-own-assumptions rule, no deposit flow is invented; this stays owner-gated (Decision Register C3 / PK-N-8).

## CONFIRMED defects

### BUG-H001 — Live order path trusts client-supplied `subtotal`/`tax`/`shipping`; server never re-prices (price tampering)  🔴
- **Route/code:** `POST /api/orders` (`server.js:953-964`, **no auth**); consumed by `frontend/public/cart.html:1180-1208`.
- **Severity:** **P0** · **Category:** Price integrity / broken function-level authorization on money (blueprint §4 "single deterministic, versioned, auditable price"; §15 L2-pricing is server-authoritative).
- **Root cause:** `/api/orders` destructures `subtotal, tax, shipping` straight from `req.body` and computes `total = subtotal + (tax||0) + (shipping||0)` (`server.js:958-964`). It **reads the cart** (`server.js:1013`) *only* to compute manufacturer-cost/margin metadata — it **never recomputes the authoritative subtotal from the cart's server-side price snapshots**, and never calls `extendedPricingEngine` or `calculate-order-total`. Whatever money numbers the client sends become `order.subtotal/tax/total` and are then copied verbatim into the auto-generated customer invoice (`server.js:1103`). The correct re-pricing logic exists in the sibling `/api/checkout`/`createOrderFromCart` path but that path is orphaned (H005). This is the classic "trust the client's cart total" hole on the one path the store actually uses.
- **Real-time example:** the legitimate client already sends browser-computed money — `cart.html:1184-1198` sets `tax = subtotal * taxRate` and `shipping = subtotal > 99 ? 0 : 9.99` in JavaScript and POSTs `{subtotal, tax, shipping}`. Since the server echoes these, a direct `POST /api/orders {sessionId:<real cart>, customerEmail, subtotal:0.01, tax:0, shipping:0, paymentMethod:'stripe', paymentStatus:'paid'}` yields a **real, fully-paid order + auto-invoice** for the real cart items priced at one cent. **[NEEDS-WRITE-TEST]** to observe the persisted order (would create an order + invoice + mutate customer stats; not run per read-only rule). Confirmed by code: the client values are stored unconditionally at `server.js:1055-1080`.
- **Proposed fix (native-first, recommendation only):** stop trusting client money on `/api/orders`. Either (a) route the storefront to the existing `/api/checkout`/`createOrderFromCart` (which re-prices from cart snapshots) and retire `/api/orders` for storefront use, or (b) in `/api/orders`, ignore body `subtotal/tax/shipping` and recompute from the server-side cart via `extendedPricingEngine` (the same call `calculate-order-total` already makes), using the client numbers only for a mismatch-reject guard (`PRICE_VALIDATION_FAILED`). In native Shopify this is intrinsic — Checkout prices server-side; the custom backend must mirror that.

### BUG-H002 — Client dictates `paymentStatus:'paid'` with zero server-side payment verification (fake-paid orders)  🔴
- **Route/code:** `POST /api/orders` (`server.js:959,1061-1066`); client sets it at `cart.html:1201`.
- **Severity:** **P0** · **Category:** Payment integrity / auth bypass on financial state.
- **Root cause:** `paymentStatus` is taken from `req.body` and written to `order.payment.status` with `processedAt` stamped when it equals `'paid'` (`server.js:1063-1065`) — the server **never confirms a charge actually settled**. The frontend literally decides paid-vs-pending in the browser: `paymentStatus: paymentMethod === 'invoice' ? 'pending' : 'paid'` (`cart.html:1201`). Nothing correlates the order to a verified Stripe `paymentIntent` or PayPal capture; the passed `paymentDetails.transactionId`/`paymentIntentId` are stored but never validated against the processor. Compounding it, the demo processor `POST /api/payments/demo/process` returns `success:true` for essentially any card except one test-decline number (`payment-routes.js:495-538`), and its result is not bound to the order either.
- **Real-time example:** a caller can POST `/api/orders` with `paymentMethod:'stripe', paymentStatus:'paid'` and no real payment; the order is created "paid," an auto-invoice is generated (cross-ref G004: invoice reconciliation also never checks back), and the order enters fulfillment as if funded. **[NEEDS-WRITE-TEST]** to persist; unconditional by code (`server.js:1061-1066`).
- **Proposed fix:** derive payment status server-side from a verified processor result, never from the request body. For Stripe, confirm the `PaymentIntent` server-side (`stripe.paymentIntents.retrieve` → require `status==='succeeded'` and `amount === order.total*100`) before marking paid; for demo mode, mark `pending`/`authorized` only. Treat `payment_intent.succeeded` webhook (`payment-routes.js:580`) as the source of truth (requires H007 fix so it can match the order).

### BUG-H003 — Live order path has no input validation: accepts missing email/name/address and an empty cart  🟠
- **Route/code:** `POST /api/orders` (`server.js:953-1121`).
- **Severity:** **P2** · **Category:** Input validation / order data integrity.
- **Root cause:** unlike `/api/checkout` (which enforces `customer.name && customer.email`, `server.js:1197`, and empty-cart via `order-service.js:83`), `/api/orders` performs **no validation at all**. `customerName/Email/Phone/address` are optional — with all blank, `customer` stays `null`, `customerId:null`, and an order is still created (an unreachable, un-invoiceable order). There is **no empty-cart guard**: if `db.cart.filter(session_id)` is empty, `cartItems=[]` and the order is created with `items:[]` while still using the client's `subtotal` — a "paid" order for zero line items. No email-format, address-completeness, or state/ZIP validation either.
- **Real-time example:** `POST /api/orders {sessionId:'nonexistent', subtotal:500, tax:36.25, paymentStatus:'paid'}` → order with `items:[]`, `customer:null`, `total:536.25`. **[NEEDS-WRITE-TEST]** to persist; guards are simply absent in code (contrast `server.js:1194-1199` on the checkout path).
- **Proposed fix:** add the same guards `/api/checkout` already has — require a non-empty cart for `sessionId`, require `customerEmail` (validated format) + name + a complete shipping address, and reject otherwise with `400`. Simplest native-first move: retire `/api/orders` for the storefront and use `/api/checkout` (H005), which already validates.

### BUG-H004 — Coupons / discounts are never applied at checkout (9.4)  🟠
- **Route/code:** `POST /api/calculate-order-total` (`server.js:1558-1633`) and `POST /api/orders` (no discount field at all).
- **Severity:** **P2** · **Category:** Missing feature / pricing (journey 9.4 "apply coupon / automatic discount").
- **Root cause:** `calculate-order-total` accepts `promoCode` (`server.js:1560`) but hardcodes the summary as `discount: { code: null, amount: 0, description: null }` (`server.js:1619`) — it never looks the code up or subtracts anything. The only promo logic, `POST /api/v1/promo/validate` (`server.js:14078`), is behind `apiKeyAuth` (external API, not the storefront), only **validates + returns** a computed discount, never persists it to a cart/order, and is called by no frontend. So a customer can enter a valid coupon and it silently does nothing.
- **Real-time example (reproduced, read-only):** `POST /api/calculate-order-total {items:[{productId:'b23180d5-…',width:24,height:36,quantity:1,options:{}}], promoCode:"SAVE10"}` → `subtotal 40`, `discount {"code":null,"amount":0,...}`, `grandTotal 52.89`. `SAVE10` is a defined active 10% code (`server.js:14085`); the total is unchanged.
- **Proposed fix (owner-gated on whether coupons are in scope):** if coupons are a real feature, wire `calculate-order-total` (and the order path) to the promo lookup — validate `promoCode` against `db.promotions`, enforce `minPurchase`, compute the discount, subtract before tax, and persist `{code, amount}` onto the order + invoice. If coupons are **not** in scope, remove the `promoCode` param and any coupon UI so it isn't silently accepted. Native-first: Shopify Discounts/Functions own this.

### BUG-H005 — Two divergent checkout paths: the safe re-pricing path is orphaned, the unsafe client-trust path is live  🟠
- **Route/code:** live `POST /api/orders` (`server.js:953`) vs dead `POST /api/checkout` (`server.js:1189`) → `createOrderFromCart` (`order-service.js:78`).
- **Severity:** **P2** · **Category:** Architecture / duplicate competing systems (same rule as BUG-A001; root enabler of H001–H004).
- **Root cause:** the codebase has **two order-creation implementations with opposite security postures**. `/api/checkout`/`createOrderFromCart` re-prices from server-side cart snapshots, validates price freshness+parity, guards empty carts, validates the customer, records status history + audit log, and auto-assigns a manufacturer. `/api/orders` does none of that and trusts the client. The storefront (`cart.html:1204`) calls **`/api/orders`**; a grep of `frontend/public` finds **zero** references to `/api/checkout`. The hardened path is effectively dead code while the store runs on the weak one — so every fix for H001–H004 already exists in the tree but is not reachable by customers.
- **Real-time example:** `grep -rn "/api/checkout" frontend/public` → no matches; `cart.html` order submission → `fetch('/api/orders', …)`. Confirmed both by code and by the endpoint-usage scan.
- **Proposed fix:** converge on the safe path — point the storefront checkout at `/api/checkout` (adjusting its request shape to `{sessionId, customer, payment}`), then either delete `/api/orders` or reduce it to an internal admin/manual-order tool behind `authMiddleware`. One order pipeline, server-authoritative, matching the "single source of truth" rule.

### BUG-H006 — No idempotency / double-submit protection on order creation → duplicate orders + duplicate invoices  🟠
- **Route/code:** `POST /api/orders` (`server.js:953`) and `POST /api/checkout` (`server.js:1189`).
- **Severity:** **P2** · **Category:** Financial data integrity / duplicate transactions.
- **Root cause:** neither order-creation route accepts or checks an idempotency key (the idempotency map in `payment-routes.js:93-129` guards only Stripe *intent creation*, not order creation). A double-click, network retry, or replay POSTs twice and creates two orders. On `/api/orders` the cart is cleared after the first (`server.js:1097`), so the **second identical POST still succeeds** — creating a second order with the client `subtotal` but `items:[]` (empty cart), a second auto-invoice, and double-incrementing `customer.totalSpent`/`totalOrders` (`server.js:1090-1092`). The submit button is disabled client-side (`cart.html:1046`) but that is not a server guard.
- **Real-time example:** two rapid `POST /api/orders` with the same `sessionId` → order #1 has the items, order #2 has `items:[]` + a duplicate invoice + inflated customer spend. **[NEEDS-WRITE-TEST]** to persist; deterministic from the clear-cart-then-no-guard sequence in code.
- **Proposed fix:** require a client-generated idempotency key (or hash of `sessionId`+cart signature) on order creation; if an order already exists for that key within a TTL, return the original order instead of creating a new one (reuse the `idempotencyCache` pattern already in `payment-routes.js`). Native Shopify Checkout is idempotent by design.

### BUG-H007 — Stripe intent carries no `orderId`, so the payment webhook can never reconcile the order (orphaned payment truth on failure/success)  🟡
- **Route/code:** intent metadata built at `cart.html:1114-1124` (only `customerEmail`); webhook matches on `o.id === paymentIntent.metadata.orderId` (`payment-routes.js:585-593`, also `.payment_failed` `:605`).
- **Severity:** **P3** · **Category:** Payment/order reconciliation / orphaned state.
- **Root cause:** the live flow creates the order **after** the browser confirms payment, and the Stripe PaymentIntent is created with **no `orderId`** in metadata (the order does not exist yet at intent time, and `cart.html` never back-fills it). Consequently the server-side webhook — the only authoritative "did money actually move" signal — can never find the order (`metadata.orderId` is `undefined`), so neither `payment_intent.succeeded` nor `payment_intent.payment_failed` ever updates an order's `paymentStatus`. If the browser dies between a successful charge and the `createOrder` call, the customer is **charged with no order recorded** and nothing reconciles it; conversely a failed charge produces no failed-order record. The order's paid state is therefore only ever what the client asserted (see H002), with no server backstop.
- **Real-time example:** `cart.html:1120` sets `metadata:{customerEmail}` only; `payment-routes.js:587` looks up by `metadata.orderId` → always miss for storefront intents. Confirmed by code.
- **Proposed fix:** create the order first (as `order_placed`/`pending`), pass its id as `metadata.orderId` into the PaymentIntent, and let the webhook drive `paymentStatus` (paid/failed) — making the server the source of truth and closing the charged-but-no-order gap. This is the standard native pattern.

### BUG-H008 — No inventory / availability check at checkout; out-of-stock or inactive products can be ordered  🟡
- **Route/code:** `POST /api/orders`, `POST /api/checkout`, `POST /api/calculate-order-total` — none read `stock_status`/`is_active`.
- **Severity:** **P3** · **Category:** Availability / oversell.
- **Root cause:** products carry `stock_status` (`in_stock`/`out_of_stock`, settable via admin at `server.js:1942`) and `is_active`, but no checkout or order-creation path consults either. A cart line for an `out_of_stock` or `is_active:false` product proceeds to a paid order.
- **Real-time example:** `db.products[0]` has `stock_status:'in_stock'`, `is_active:true`; a grep of the order/checkout/total routes (`server.js:953-1121`, `1558-1637`) for `stock|inventory|avail` returns nothing — the field is never checked.
- **Proposed fix:** on order creation, re-validate each line's product `is_active !== false` and `stock_status !== 'out_of_stock'`; reject with a clear "no longer available" message (native Shopify blocks out-of-stock at checkout automatically). For a made-to-order model, if stock is not meaningful, remove/repurpose the `stock_status` field so it isn't a dangling half-feature.

## Summary
**8 confirmed Stage-9 checkout/payment defects — the live storefront runs on an unauthenticated `/api/orders` path that trusts client-supplied money and payment status, re-prices nothing, validates nothing, applies no coupons, and has no idempotency, while the hardened `/api/checkout` path that does all of this sits orphaned.** Counts: **P0: 2** (H001 price tampering, H002 fake-paid orders) · **P1: 0** · **P2: 4** (H003 no validation/empty-cart, H004 coupons never applied, H005 orphaned safe path, H006 no idempotency) · **P3: 2** (H007 webhook can't reconcile, H008 no inventory check). Deposit/terms (9.3) remains an owner-gated documented gap (cross-ref stage-14). All findings are code-confirmed; write-dependent reproductions marked **[NEEDS-WRITE-TEST]**. No fixes applied; DB unchanged (md5 `806f71056b2e24945c90bd3de893083d`).
