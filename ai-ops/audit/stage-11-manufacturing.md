# Stage 11 — Manufacturing (Manufacturing Agent) — Audit

> Section **K** of the recursive audit loop. Scope: customer-journey **Stage 11** — 11.1 generate manufacturer work order from the order spec, 11.2 production status + QA milestones, 11.3 defect/rework — plus the manufacturer portal's read/write surface, manufacturer assignment, status sync, and manufacturer cost/payable handling. Reproduced **read-only** against the running app on `http://localhost:3001` with sample data in `backend/database.json` (12 orders, 1 active manufacturer `mfr-zstarr`, 1 manufacturer user `manufacturer@peekaboo.com`). No fixes applied; recommendation-only. RBAC (§15.1) general auth-gating already fixed (BUG-D001/D002) and not re-litigated — but manufacturer-portal cross-tenant / financials leaks **are** in scope and reported below.
>
> **Read-only discipline note:** every reproduction used GET plus the two task-authorized login POSTs. `authenticateManufacturer()` writes a `lastLogin` timestamp on each successful login (`manufacturer-service.js:97-100`), so the two manufacturer logins updated that single benign field; no other DB mutation was made and no `product.html` / write endpoint was touched. Pre-audit md5 of `database.json` recorded as `0c2ce81105607cb03d8c89817ad36dde` for the record.

## What is already correct (verified, no change)
- **Perimeter auth is sound.** `manufacturerAuthMiddleware` requires a valid token **and** `decoded.role === 'manufacturer'` (`server.js:9495`); admin `authMiddleware` rejects the manufacturer role (D001 fix). Manufacturer tokens don't reach `/api/admin/*` and vice-versa.
- **`/status` enforces the manufacturer transition matrix.** `updateOrderStatus` blocks an out-of-matrix transition: `if (!allowedTransitions.includes(newStatus)) throw` (`manufacturer-service.js:266`). A manufacturer **cannot** set an arbitrary illegal state through this endpoint (e.g. `order_received`→`shipped` is rejected here).
- **Assignment scoring is reasonable.** `findBestManufacturerForOrder` prefers a manufacturer that handles *all* product types in the order and has active pricing for them, with `assignmentPriority` as tiebreak, and falls back to the first active manufacturer (`manufacturer-assignment-service.js:151-219`). `manualAssignManufacturer` validates the manufacturer exists and is `active` (`:303-310`).
- **Status changes via `/status` are audited.** `updateOrderStatus` appends to `db.orderStatusHistory` and writes an `ORDER_STATUS_CHANGE` audit record (`manufacturer-service.js:288-315`).
- **Tracking is written to the canonical field.** `addTrackingInfo` correctly writes to `order.tracking` (not `order.shipping`, which holds the numeric cost) per the earlier BUG-F002/F003 fixes (`manufacturer-service.js:340-348`) and queues a shipment-notification `emailLog`.

## CONFIRMED defects

### BUG-M001 — Manufacturer JWT omits `manufacturerId`; the production queue shows only UNASSIGNED orders and hides all of the manufacturer's real work (and breaks pricing upload)  🔴
- **Route/file:** `generateToken` (`middleware/auth.js:74-91`); consumed by `getManufacturerOrders` (`manufacturer-service.js:110-123`) and the pricing endpoints (`server.js:3384,3415,3488,3508`).
- **Severity:** **P1** · **Category:** Data integrity / broken order→manufacturer scoping + feature outage.
- **Root cause:** `POST /api/manufacturer/login` calls `generateToken({... manufacturerId: user.manufacturerId, manufacturerName })` (`server.js:9470-9477`), but `generateToken` **whitelists only** `id, email, name, role` (+ `dealerId`/`dealerName`). It silently drops `manufacturerId`. Every manufacturer request therefore has `req.manufacturer.manufacturerId === undefined`. In `getManufacturerOrders(undefined)` the ownership guard `if (o.manufacturerId && o.manufacturerId !== manufacturerId) return false` evaluates `"mfr-zstarr" !== undefined` → **true** for every assigned order, so **all assigned orders are dropped** and only orders with a falsy `manufacturerId` survive. The manufacturer's queue thus shows the opposite of what it should: orphan/unassigned orders, never their own.
- **Real example (reproduced, live):** decoded manufacturer token payload = `{"id":"mfr-user-e23820d6","email":"manufacturer@peekaboo.com","name":"Factory Manager","role":"manufacturer",...}` — **no `manufacturerId`**. `GET /api/manufacturer/stats` → `{pending:1,inProduction:1,shipped:5,totalActive:2}` (7 orders), but `GET /api/manufacturer/orders` → `total:1`, returning only the unassigned `ORD-TEST-1768836005920`. The 5 shipped + 1 manufacturing orders assigned to `mfr-zstarr` are invisible in the queue. Same root cause makes `GET /api/manufacturer/pricing-status` and `/upload-history` return **`{"success":false,"error":"Invalid manufacturer token"}`** for the legitimate manufacturer (the handlers require `decoded.manufacturerId`), so pricing upload is entirely non-functional.
- **Proposed fix (native-first, recommendation-only):** in `generateToken` add the manufacturer claims when present (`if (user.manufacturerId) payload.manufacturerId = user.manufacturerId; if (user.manufacturerName) payload.manufacturerName = user.manufacturerName;`), mirroring the existing dealer branch. Re-test that the queue then lists the assigned orders — which will immediately surface BUG-M003 scoping in the detail/write endpoints, so fix M003 in the same pass.

### BUG-M002 — Manufacturer order-detail leaks CUSTOMER financials + full PII to the manufacturer  🔴
- **Route/file:** `getManufacturerOrderDetail` (`manufacturer-service.js:169-248`) via `GET /api/manufacturer/orders/:orderId` (`server.js:9528`).
- **Severity:** **P1** · **Category:** Cross-role financials/PII leak (blueprint §15.1 "manufacturers never see customer financials … margin is internal").
- **Root cause:** the detail projection returns customer *retail* economics next to manufacturer cost: `pricing.subtotal/tax/total` (customer prices), `customerInvoice.{invoiceNumber,total}`, and per-item `unitPrice`/`lineTotal`/`price_breakdown` — none of which a manufacturer should see. Only `manufacturerCost`/`manufacturerInvoice` are legitimately theirs. Because customer total and manufacturer cost are returned together, the manufacturer can trivially derive the store's margin.
- **Real example (reproduced, manufacturer token):** `GET /api/manufacturer/orders/ORD-MKA1VL9O` → `customer:{name:"Surya",email:"Surya@gmail.com",phone:"8169449009",address:"205 Blue Jasmine Trl, Georgetown, TX 78628, US"}`, `pricing:{subtotal:630.51,tax:52.017075,total:732.53,manufacturerCost:405.34}`, `customerInvoice:{invoiceNumber:"INV-MKA1VLA1E0ZC",total:732.53}`. Margin (732.53 − 405.34 = 327.19, ~52%) is exposed to the factory.
- **Proposed fix:** return a manufacturer-safe projection — drop `pricing.subtotal/tax/total`, `customerInvoice`, and item `unitPrice/lineTotal/price_breakdown`; keep only fabric code, dimensions, options, quantity, room, notes, `manufacturerCost`, and `manufacturerInvoice`. (The Stage-14 G002 print projection is a good template.) PII (name/address) is needed for the shipping label and can stay, but retail money must not.

### BUG-M003 — No manufacturer scoping on detail/status/tracking → cross-manufacturer IDOR and cross-manufacturer actions  🔴
- **Route/file:** `getManufacturerOrderDetail` (`manufacturer-service.js:171`), `updateOrderStatus` (`:256`), `addTrackingInfo` (`:326`) — each does `db.orders.find(o => o.id === orderId || o.order_number === orderId)` and **never checks `order.manufacturerId === manufacturerId`**.
- **Severity:** **P1** · **Category:** Broken access control / cross-tenant (blueprint §15.1 "zero unauthorized cross-role access"; task focus "a manufacturer act on another manufacturer's orders").
- **Root cause:** the `manufacturerId` argument is accepted by all three functions and then ignored for authorization (it's used only to stamp history). Any manufacturer can read, re-status, or ship any order by id/number regardless of assignment. Today this is masked by BUG-M001 (undefined id) but the missing check is independent of it — once M001 is fixed the scoping is still absent.
- **Real example (read, reproduced):** manufacturer token fetched full detail of both the **unassigned** `ORD-TEST-1768836005920` and the assigned `ORD-MKA1VL9O` with no ownership error (see M002 output). With a second manufacturer in the data, `mfr-B` could `GET`/`POST .../status`/`.../tracking` on `mfr-A`'s orders identically. **[NEEDS-WRITE-TEST]** for the status/tracking write paths (writes were not executed per read-only rule), but the missing guard is the same line-of-code omission as the reproduced read.
- **Proposed fix:** in all three functions, after locating the order, return 404/throw unless `order.manufacturerId === manufacturerId` (allow a null-assignment escape only if the business intends a shared pool — see M009). Add a regression test: `mfr-B` token → 404 on `mfr-A`'s order.

### BUG-M004 — `addTrackingInfo` bypasses `MFR_VALID_TRANSITIONS` and force-ships from any state; ship event written to the wrong history array  🟠
- **Route/file:** `addTrackingInfo` (`manufacturer-service.js:352-363`) via `POST /api/manufacturer/orders/:orderId/tracking` (`server.js:9561`).
- **Severity:** **P2** · **Category:** Illegal state transition + status-history divergence.
- **Root cause:** unlike `/status`, the tracking path does **not** consult `MFR_VALID_TRANSITIONS`. It sets `order.status = 'shipped'` for any order not already in a terminal state (`['shipped','delivered','closed','cancelled','refunded']`). So an order in `order_received` (never manufactured, never QA'd) jumps straight to `shipped` on a tracking POST — the exact skip the `/status` guard is meant to prevent. Additionally it appends the transition to the **embedded** `order.status_history`, whereas the portal detail reads the **global** `db.orderStatusHistory` (`manufacturer-service.js:178`), so the ship never appears in the timeline the portal renders, and no `ORDER_STATUS_CHANGE` audit record is written (only an `ORDER_UPDATE`).
- **Real example:** `ORD-TEST-1768836005920` is in `order_received`; a tracking POST would set it to `shipped` (skipping `manufacturing`/`qa`/`ready_to_ship`) and record that only in `order.status_history`, invisible in `GET /api/manufacturer/orders/:id` → `statusHistory`. **[NEEDS-WRITE-TEST]** (write path not executed).
- **Proposed fix:** gate the auto-ship in `addTrackingInfo` behind `MFR_VALID_TRANSITIONS[order.status]?.includes('shipped')` (or require the order already be `ready_to_ship`/`qa`), and write the transition through the same `db.orderStatusHistory` + audit path `updateOrderStatus` uses so the timeline stays coherent.

### BUG-M005 — Manufacturer-driven shipping never records the profit/payable-paid ledger  🟠
- **Route/file:** `recordShippedProfit` (`ledger-service.js:196`) is called **only** from admin `PUT /api/admin/orders/:id/status` (`server.js:2369`). `manufacturer-service.js` has **zero** ledger references (grep confirmed).
- **Severity:** **P2** · **Category:** Financial data integrity / reconciliation gap.
- **Root cause:** shipping is a manufacturer action per `ORDER_LIFECYCLE.md` §3.2 ("Manufacturer Can… Ship"), and the portal's `/status` (`qa`→`shipped`) and `/tracking` (force-ship) are the natural way it happens. But neither `updateOrderStatus` nor `addTrackingInfo` invokes `recordShippedProfit`, so the `MANUFACTURER_PAID` + `MARGIN_EARNED` / realized-profit entries (created for the admin path) are never written when the manufacturer ships. Profit is silently unrecorded for every portal-shipped order.
- **Real example:** admin `PUT /status {status:'shipped'}` logs `Profit recorded for order …` (`server.js:2370`); the equivalent manufacturer `POST /api/manufacturer/orders/:id/status {status:'shipped'}` returns `{success:true}` with **no** ledger write — the order's profit is never realized. **[NEEDS-WRITE-TEST]** to diff `getEntriesForOrder` before/after a portal ship.
- **Proposed fix:** call `recordShippedProfit(order.id)` (guarded by `previousStatus !== 'shipped'`, with the same `db-loader.invalidateCache()` coherence step used at `server.js:2368`) inside the manufacturer ship transition — ideally in one shared helper the admin and manufacturer paths both call, so profit posts exactly once regardless of who ships.

### BUG-M007 — Orders in `pending` status are invisible and unactionable to the assigned manufacturer  🟠
- **Route/file:** status set at order creation `status: 'pending'` (`server.js:1059`); consumed by `getManufacturerOrders`/`getManufacturerStats` (`manufacturer-service.js:121,409`) and `MFR_VALID_TRANSITIONS` (`:21`).
- **Severity:** **P2** · **Category:** Status-model mismatch / stuck orders.
- **Root cause:** `pending` is not a member of `MFR_ORDER_STATUSES` (`order_received|manufacturing|qa|ready_to_ship|shipped`) and is not a key in `MFR_VALID_TRANSITIONS`. So a `pending` order is filtered out of both the queue and the stats, and `updateOrderStatus` on it computes `allowedTransitions = MFR_VALID_TRANSITIONS['pending'] || [] = []` → throws `Cannot transition from pending to …`. `pending` is also absent from `ORDER_LIFECYCLE.md`'s state list entirely (the doc uses `order_received`), so it's an undocumented status the manufacturer workflow can neither see nor advance.
- **Real example (reproduced):** four orders assigned to `mfr-zstarr` — `ORD-MKJ3SCE2`, `ORD-MKJ4HIDX`, `ORD-MKJ4NY1H`, `ORD-MKJ4TFA8` — all sit in `pending` and are absent from `getManufacturerStats` output and the queue; a manufacturer can never start production on them.
- **Proposed fix:** decide the canonical "ready to manufacture" status and make it consistent — either normalize new orders' post-payment status to `order_received` (the documented state) rather than `pending`, or add `pending` to `MFR_ORDER_STATUSES`/`MFR_VALID_TRANSITIONS` (`pending → manufacturing`). Confirm with the owner which is intended before changing order-creation defaults.

### BUG-M006 — `ready_to_ship` is an orphan state unknown to the canonical order state machine  🟡
- **Route/file:** `MFR_VALID_TRANSITIONS` defines `qa → ['ready_to_ship', 'manufacturing']` and `ready_to_ship → ['shipped','qa']` (`manufacturer-service.js:21-27`), but `order-service.js` `VALID_TRANSITIONS` (`:28`) and the admin route `validStatuses` array (`server.js:2263-2282`) contain **no** `ready_to_ship`, and `ORDER_LIFECYCLE.md` §2/§3 omit it.
- **Severity:** **P3** · **Category:** Spec drift / cross-system state inconsistency.
- **Root cause:** the `ready_to_ship` status was added to the manufacturer subset (and the production-queue UI) without being added to the canonical machine. An order the portal moves to `ready_to_ship` is a status the admin `PUT /status` route rejects as `Invalid status` and the `order-service` transition validator doesn't recognize, so admin-side tooling can't act on it.
- **Real example:** `ORDER_LIFECYCLE.md` §3.1 even documents `MFR_VALID_TRANSITIONS` as `qa: ['shipped','manufacturing']` (no `ready_to_ship`), directly contradicting the shipped code — the doc and code disagree, and neither matches `order-service.VALID_TRANSITIONS`.
- **Proposed fix:** pick one source of truth. Either add `ready_to_ship` to `order-service.VALID_TRANSITIONS` + the admin `validStatuses` list + `ORDER_LIFECYCLE.md`, or remove it from the manufacturer subset. Owner decision on whether `ready_to_ship` is a real business state.

### BUG-M008 — `getManufacturerStats` ignores `manufacturerId` and counts every manufacturer's orders  🟡
- **Route/file:** `getManufacturerStats` (`manufacturer-service.js:404-421`).
- **Severity:** **P3** · **Category:** Cross-tenant count leak / integrity.
- **Root cause:** the stats filter checks only `mfrStatuses.includes(o.status)` — it never filters by `manufacturerId` (the parameter is accepted and unused). With more than one manufacturer, each portal shows global counts including other factories' order volumes. It's also why the dashboard (7) disagreed with the M001-broken queue (1) during this audit.
- **Real example (reproduced):** `getManufacturerStats` returned `shipped:5, totalActive:2` counting all `mfr-zstarr` + unassigned orders; had a second manufacturer's orders existed, they'd be counted too. Harmless with one manufacturer today, but a scoping defect.
- **Proposed fix:** filter `mfrOrders` by `o.manufacturerId === manufacturerId` (matching the intended queue scope) before counting.

### BUG-M009 — No auto-assignment at checkout; orders reach `order_received` unassigned and orphan orders leak into every manufacturer's queue  🟡
- **Route/file:** order creation (`server.js:1046-1213`) never calls `autoAssignManufacturer`; `getUnassignedOrders`/`getManufacturerOrders` scoping (`manufacturer-assignment-service.js:385`, `manufacturer-service.js:116`).
- **Severity:** **P3** · **Category:** Assignment workflow gap / cross-tenant visibility of orphan orders.
- **Root cause:** assignment is only ever triggered by the admin endpoints (`assign-manufacturer`, `auto-assign-all`); nothing assigns a manufacturer when the order is created or when payment is confirmed, so an order can advance to a manufacturer-relevant status with `manufacturerId === null`. Meanwhile `getManufacturerOrders`'s guard `if (o.manufacturerId && …)` lets unassigned orders pass for **every** manufacturer, so an orphan order surfaces in all portals at once (and, given M001, is the *only* thing that surfaces).
- **Real example (reproduced):** `ORD-TEST-1768836005920` is `order_received` with `manufacturerId: NONE` and appears in `mfr-zstarr`'s `GET /api/manufacturer/orders` (`total:1`). Stage 11.1 ("generate work order from order") has no automatic trigger — the order reaches the manufacturing stage with no assigned manufacturer.
- **Proposed fix:** call `autoAssignManufacturer(order.id)` when an order transitions to `order_received` (payment confirmed), and make `getManufacturerOrders` exclude unassigned orders (or route them to an explicit admin "unassigned" bucket rather than leaking into a manufacturer's queue). Owner decision on whether auto-assign should run at checkout vs. at payment confirmation.

### BUG-M010 — Manufacturer pricing-upload endpoints use hand-rolled `jwt.verify` instead of `manufacturerAuthMiddleware` (inconsistent auth; role never checked)  🟡
- **Route/file:** `GET /api/manufacturer/pricing-template` (`server.js:3376`), `POST /api/manufacturer/upload-pricing` (`:3407`), `GET /api/manufacturer/pricing-status` (`:3480`), `GET /api/manufacturer/upload-history` (`:3501`).
- **Severity:** **P3** · **Category:** Inconsistent auth pattern (+ consequently broken feature via M001).
- **Root cause:** these four routes each re-implement auth with `jwt.verify(token, JWT_SECRET)` and only assert `decoded.manufacturerId` — they never assert `role === 'manufacturer'` or that the manufacturer user is active, unlike the shared `manufacturerAuthMiddleware`. `POST /upload-pricing` then mutates `manufacturerPrices` (which drives customer pricing). Any future non-manufacturer token that happened to carry a `manufacturerId` claim would pass. Today the same code is also **broken** for the real manufacturer because M001 strips `manufacturerId` from the token (reproduced: both `pricing-status` and `upload-history` return `Invalid manufacturer token`).
- **Real example (reproduced):** `GET /api/manufacturer/pricing-status` with the legitimate `mfr123` token → `{"success":false,"error":"Invalid manufacturer token"}`.
- **Proposed fix:** replace the inline `jwt.verify` blocks with `manufacturerAuthMiddleware` and read `req.manufacturer.manufacturerId` (after M001 restores the claim), so all manufacturer routes share one auth path that checks role.

## Summary
Stage 11 manufacturing has **10 confirmed defects**: a token-serialization bug (M001) breaks the manufacturer's own production queue and pricing upload; the manufacturer portal leaks customer financials + PII (M002) and has no cross-manufacturer scoping on read or write (M003); the tracking path force-ships past the transition guard into the wrong history array (M004); manufacturer-driven shipping never records profit (M005); and `pending`/`ready_to_ship` state drift plus missing auto-assignment leave orders invisible, orphaned, or unrecognized (M006–M010). All are backend/native fixes with no front-end redesign; write-path items are tagged **[NEEDS-WRITE-TEST]**.

**Counts by severity:** P0: 0 · **P1: 3** (M001, M002, M003) · **P2: 3** (M004, M005, M007) · **P3: 4** (M006, M008, M009, M010) · P4: 0.
