1. Executive Summary

PeekabooShades sells custom, made-to-measure indoor and outdoor window treatments. To operate at enterprise scale it must run like a modern commerce business: a design-led Shopify storefront, a deterministic made-to-measure pricing engine, multi-party fulfillment (manufacturer → shipping → installer), partner channels (dealer, designer, realtor, affiliate), and a finance and analytics backbone — all governed by security, reliability and compliance controls.

This blueprint defines the target platform and a disciplined, approval-gated delivery method. It adopts the client's mandate that all work follow a recursive engineering lifecycle (Discover → Map → Research → Design → Implement → Test → Deploy → Monitor → Detect → Root-cause → Fix → Retest downstream → Redeploy) and a strict native-Shopify-first capability order, with no front-end redesign unless a verified defect requires it.

Principal architectural finding (evidence-based, not assumed). The store runs on the Shopify Basic plan. Shopify B2B / Companies / customer-specific catalogs are Plus-only and therefore unavailable today. Consequently, the existing custom backend must remain the system of record for partner accounts, custom/dealer pricing, quotes, work orders, installer assignments and commissions, while Shopify remains authoritative for products, customers, cart, checkout, orders, payments and fulfillment. [CONFIRM: is a future upgrade to Shopify Plus in scope? It materially changes what can be native.]

Approach. Two programs run in a controlled parallel: Program A — Enterprise Engineering (audit → fix → align → complete the platform) runs first and continuously; Program B — AI/MLOps runs its design-only phases in parallel and gates its build phases on Program A delivering clean data, stable APIs and consent-compliant capture. Every change is reproduced, justified with a real-time example, approved, applied as the smallest safe change on a feature branch, tested, and retested downstream — never on main.

  • Audit, correction and completion of the Shopify store, theme, Admin configuration, backend services, APIs, webhooks and all portals (admin, dealer, manufacturer, installer, plus new: interior-designer, realtor, affiliate, customer).

5. Governance & Operating Model

5.1 Change-control & approval gates

Change-control rule. No code, design or configuration change proceeds without: (1) reproduction of the issue, (2) written justification, (3) a concrete real-time example, (4) owner approval, (5) the smallest safe change, (6) test + downstream retest, (7) deployment to a feature branch — never main — and (8) monitoring. 6. Requirements Baseline & Traceability (the Mandate)

The client's “Mandatory Shopify, GitHub, Admin-Portal and Recursive Engineering Module” (21 numbered sections) is adopted verbatim as the binding requirements baseline. Its core directives: operate as a recursive lifecycle (never stop at an audit); apply the native-Shopify-first order; protect the front-end design; audit every repository, page, portal, API and webhook; produce a defined set of architecture deliverables; and prioritize fixes security → payment/invoice → pricing → data-loss → orders → permissions → integrations before any enhancement.

6.1 Non-negotiable directives (extracted)

  • Do not stop after producing an audit — run the full recursive fix loop.
  • Native-first order (§6.3 below) governs every feature decision; never build custom merely because it is possible; never replace a working native feature.
  • Verify plan/feature/limits/B2B/API before use — never assume a feature is free or available.
  • Front-end protection — preserve branding, logo, typography, palette, product cards, layout, navigation, spacing, responsive behavior; smallest possible UI change with before/after screenshots + visual-regression + approval.
  • One source of truth per data domain; do not maintain two competing systems.
  • Pricing must be deterministic, versioned, reproducible; never store only the total; any cross-surface mismatch is a critical defect.
  • Least-privilege RBAC with the stated hard rules (manufacturers can't see customer financials; installers see only assigned jobs; etc.).
  • Do not proceed to unrelated enhancements while P0/P1 defects exist.
  • Start with architecture, data flow, source-of-truth, permissions, functional testing and defect inventory — not visual design, not blog posts, not replacing working code.

7. Guiding Engineering Principles

7.1 Native-Shopify-first capability order (binding)

Existing Shopify native -> Admin config -> theme section/block/template -> metafields
 -> metaobjects -> products/variants/collections -> customer accounts
 -> Companies/B2B/payment terms (when plan supports) -> draft orders/orders/discounts/invoices
 -> Shopify Forms / official capability -> Shopify Flow -> installed app that already meets need
 -> free official app (after security & limit check) -> existing GitHub backend service
 -> Admin/Storefront/Customer-Account API or webhooks -> Shopify Functions
 -> custom backend code -> paid app (documented business case)
 -> new custom frontend (only when no safe native option, with owner approval)

Rules: do not create custom code merely because it is possible; do not replace a working native feature; do not force a free solution that creates security/scalability/reliability/operational risk. Verify plan, feature availability, usage & API limits, checkout-customization limits, B2B availability, customer-account capabilities, Flow capabilities, app pricing/permissions/maintenance before use.

7.2 Front-end protection

Preserve branding, logo, typography, palette, product-card appearance, product-page layout, navigation style, component patterns, spacing, responsive behavior, customer flow, approved images and content hierarchy. Backend logic (APIs, DB, webhooks, pricing, auth, roles, order state, invoicing, reconciliation, analytics, notifications, Functions, Flow, validation, caching, queues, security) may be corrected. Any visible change follows Gate G4.

9. Data Architecture — OLTP, OLAP & Entities

9.1 OLTP (transactional)

  • Shopify handles high-integrity commerce transactions (orders, payments, refunds).
  • Backend OLTP holds operational transactions Shopify does not model (work orders, install appointments, measurements, commissions, quote versions). [CONFIRM: migrate JSON/SQLite to a managed transactional DB (e.g. PostgreSQL) for concurrency, backups and audit — recommended.]
  • Every pricing calculation stores inputs + applied rules + pricing version + timestamp (never only the total).

9.2 OLAP (analytical) pipeline

Sources: Shopify(orders,customers,checkout) · Backend(quotes,production,installs,commissions) ·
         GA4 · Search Console · Google Business Profile · Marketing platforms · Payment/Invoice events
  -> Event collection & validation (consent-aware)
  -> Operational data store / secure integration layer (ELT)
  -> Transformation & data-quality checks
  -> Analytics warehouse (star schema: fact_orders, fact_quotes, fact_production, fact_installs,
     fact_payments, dim_customer, dim_product, dim_fabric, dim_partner, dim_date, dim_geo)
  -> Business metrics layer (revenue, pipeline, cycle time, remake rate, LTV, attribution)
  -> Dashboards (Executive / Sales / Ops / Finance / SEO / SRE)

The analytics layer is a read-only consumer; it must never update orders or financial records. [CONFIRM: warehouse/BI choice — e.g. BigQuery/Snowflake + Looker/Metabase.]

15.1 Security & RBAC

Least-privilege roles (Owner, Super Admin, Finance, Ops, Sales Mgr, Sales Rep, CS, Marketing, SEO, Analyst, Dealer, Manufacturer, Installer, Designer, Realtor, Affiliate, Customer) across actions View/Create/Edit/Approve/Assign/Export/Refund/Cancel/Delete/Change-price/Change-payment-status/Change-invoice-status/Change-production-status/Change-installation-status/Manage-users/View-sensitive-data. Hard rules: manufacturers never see customer financials; installers see only assigned jobs; dealers see only permitted customers/catalog/orders; affiliates never see payment data; analysts get masked PII; marketing cannot change financial records; no manual "payment successful" without permission + audit; critical actions audited; MFA on sensitive actions where supported. Verify webhook signatures; idempotency; secrets in a vault; minimal PII logging. [LEGAL: PCI scope — never store card data; CCPA/privacy data requests]

15.2 SRE / reliability

SLOs for storefront, pricing, checkout, portals; health checks; staged deployment; canary + automated rollback to last-known-good; incident runbooks + on-call; dead-letter queues + replay; backups with tested restore (RPO/RTO). [CONFIRM: hosting/infra & SLO targets]

15.3 Performance & accessibility

Responsive images (WebP/AVIF), lazy-load below fold (never the first hero image), no layout shift, mobile/tablet parity, keyboard access, visible focus, accessible labels. [LEGAL: ADA/WCAG conformance]

15.4 Compliance summary

Refund/cancellation terms for custom goods; sales-tax nexus & invoice compliance; PCI; privacy/CCPA; ADA/WCAG; AI disclosure & photo consent/retention; third-party (ZSTARR) asset-reuse authorization; partner/affiliate agreements. All tracked in §22.

L0 — Business flow

[Customer/Partner] -> [Storefront/Portal] -> [Config+Fabric+Options] -> [Validation] -> [Pricing]
 -> [Cart/Quote/Draft] -> [Auth+Contact] -> [Checkout/Payment/Deposit] -> [Shopify Order]

L2 — Pricing flow

Config(width,height,fabric,options,control,qty)
  -> validate dims (min/max, fractions, deduction)
  -> area = max(w*h, min_billable)
  -> perSqM = pricing_version[fabricCode][controlBand]
  -> base = area * perSqM * (1 + margin)
  -> + sum(selected option data-price, gated by control type)
  -> + shipping/install/high-ceiling ; * quantity
  -> apply dealer tier / coupon / tax (no double-stack)
  -> round(currency) -> {itemized breakdown, inputs, pricing_version, timestamp}
  -> identical value in page / cart / checkout / order / invoice / portal

Payment & invoice (sequence)

Customer -> Checkout: place order (deposit)
Shopify  -> Backend (webhook orders/paid): create project, deposit invoice
Backend  -> Customer: deposit receipt
...manufacture + install...
Backend  -> Customer: balance invoice (draft-order invoice)
Customer -> Shopify: pay balance
Shopify  -> Backend: reconcile -> mark Paid -> close

Authentication / authorization boundaries

Public storefront  | no auth
Customer account   | Shopify passwordless
Partner portals    | backend JWT, role-scoped, MFA where supported
Admin              | backend JWT + RBAC + audit
APIs / webhooks    | signed, idempotent, rate-limited, dead-letter on failure

Downstream retest rule: a pricing fix is retested across product page, cart, checkout, order, admin, invoice, dealer & manufacturer portals and analytics; an order-status fix across Shopify Admin, customer/dealer/manufacturer/installer portals, invoicing, notifications, tracking, sales dashboard and analytics.

18. Deployment, Release & Rollback

  • Feature branch → pull request → code review → automated tests → theme preview / staging → deployment checklist → staged production release → post-release monitoring.
  • Every release carries a rollback plan to the last-known-good state; main and the live theme are never edited directly.
  • Go-live requires QA sign-off (G5) and, where flagged, legal sign-off.

19. Monitoring Plan

  • Uptime/health for storefront, pricing, checkout and portals; error-rate and latency SLO alerts.
  • Webhook success/failure with dead-letter alerts and replay; reconciliation exceptions; pricing-mismatch detector.
  • Post-release regression watch — on regression, restart the recursive loop at the earliest affected phase.
